# Phase 7 - Blind Re-solving Versus Answer-visible Re-solving

**Status: completed diagnostic; blind re-solving strongly outperformed
answer-visible re-solving on the protected set. No system was promoted.**

Read the [final report](docs/FINAL_REPORT.md) for the protected result and
limitations.

Phase 6 found that even an oracle flagging an initially wrong answer led to
only 1/20 verified repairs for the original solver and 2/20 for each Phase 4
adapter on its fresh holdout. Phase 7 asks whether that low repair rate reflects
limited ability to solve the problem again, or whether showing the model its
earlier wrong answer anchors the next attempt.

The primary experiment pairs two new continuations for the same source,
checkpoint, and natural initial answer:

| Arm | Model-visible input | Purpose |
|---|---|---|
| Blind re-solve | A fresh conversation containing only the original problem and the ordinary solve instruction | Measure independent second-pass solving without answer anchoring |
| Answer-visible re-solve | The same problem and solve instruction, plus the earlier answer labeled as an unverified candidate | Measure the effect of exposing the previous answer while still asking for a fresh solution |

Neither arm receives a correctness label, verifier trace, reference answer,
probe score, or previous conversation history. The blind arm must contain **no
text, tokens, or metadata from the earlier answer**. The harness keeps the old
answer outside the model context, then compares both new answers with it and
scores all answers using the deterministic verifier. The answer-visible arm is
the paired anchoring control; it is not the old KEEP/REVISE repair task.

The three frozen project checkpoints remain the original solver, Phase 4
warm-start V2, and Phase 4 correction SFT V3. The first answer is generated by
the original solver and held fixed across arms and checkpoints. A frozen Phase
5 probe at its existing threshold may supply the non-oracle route. An
oracle-known-wrong analysis is kept separate to measure the solving ceiling
without detector errors. No weights or probes are fitted in Phase 7.

The documented Phase 5 probe artifact was unavailable throughout this run.
The paired solving test completed, but the non-oracle probe-routed result is
unavailable. No detector was newly fitted or retuned on protected data.

The CPU audit found 1,974 fresh, verifier-checked eligible problems after
Phase 1-6 exclusions and froze the first 600 in hash order. It rechecked all
286 Phase 1-4 exclusion inventory files against the earlier recorded hashes,
and excluded the full Phase 5 selected pool and Phase 6 confirmation pool.
See `data/candidates_v1/candidate_report.json`. The initial collector stopped
at 334 answers (234 correct, 100 wrong). No Phase 5 protected row, Phase
6 holdout, or prior raw answer enters selection, prompt tuning, or training.
The protected set was opened once after prompts, checkpoints, decoding,
routing, metrics, and stop rules were locked.

## GPU feasibility

The run began on a Tesla V100 32 GB, then continued on an RTX 3090 24 GB
after the V100 host disappeared. All protected paired outputs were generated
on the RTX 3090 in FP16 with vLLM 0.7.0. The original checkpoint used
19,430 MiB after the 3090 smoke; both adapters retained their Phase 5
lineage. A
16 GB NVIDIA GPU remains a **conditional fallback**. The original checkpoint has
15.23 GB of FP16 weight files before runtime and KV cache, leaving too little
room for safe full-precision inference on 16 GB. That fallback would use one checkpoint
at a time with Transformers/bitsandbytes NF4 weights, FP16 compute, batch size
one and a 2,048-token context, followed by a memory and correctness smoke
test. Merge V2 into the original FP16 solver on CPU first; run both V2 and V3
from that quantized merged V2, attaching the V3 LoRA only for V3. This requires
substantial host RAM and disk as well as the 16 GB VRAM. Quantization changes
model behavior, so Phase 7's paired arms must use the same quantized checkpoint;
historical Phase 6 FP16 rates are contextual, not a causal comparison. If the
V2 parent cannot be materialized or a model fails the GPU smoke, stop that
checkpoint rather than silently changing its lineage or precision.
